1. Product Overview

1.1 Working Title

Camino a la Copa (English title: Road to the Cup). The final title may remain in Spanish in both language versions.

1.2 Game Concept

Camino a la Copa is an arcade-style football game in which the user creates and controls one individual footballer. The player selects a name, appearance, country/team, shirt number, and playing position, then competes in an elimination tournament.

During matches, special ability circles appear on the pitch. Moving over a circle adds its ability to the player's inventory (maximum 5 stored). Abilities are activated strategically with the keyboard.

The team that scores the most goals wins. Winning advances the player to the next round; losing repeats only the current match. Level, statistics, unlocked equipment, and progression are always preserved. Winning the final grants a trophy and unlocks a new, harder tournament. The tournament sequence is infinite.

2. Target Platform

Correction: the original document targeted Android/iOS (touch) first with Unity. This edition targets an HTML5 browser game with keyboard controls, because the game will be implemented directly in HTML/JavaScript.

2.1 Primary Platform

  • Web browser (desktop): Chrome, Firefox, Safari, Edge
  • Input: keyboard (see §13); mouse only for menus (optional)
  • Presentation: landscape 16:9 canvas that scales responsively to the window
  • Distribution: static files (no build step required); playable offline once loaded

2.2 Possible Future Platforms

  • Mobile browsers / installable PWA (would reintroduce touch controls: virtual joystick + buttons)
  • Desktop wrappers (Electron/Tauri), Steam
  • Gamepad support via the Gamepad API

The input layer must be isolated (see §39) so keyboard input can later be supplemented by touch or gamepad without rewriting gameplay code.

3. Target Audience

Primary: children approximately 7–14, casual football fans, players who enjoy short matches and progression systems.

Secondary: families, teenagers, casual players, players who prefer arcade football over realistic simulation.

Visual design, controls, text, and menus must remain easy to understand for younger users. Keyboard controls must use few keys and be shown on screen at all times.

4. Design Principles

  1. Easy to learn.
  2. Short and exciting matches.
  3. Simple controls — the whole game is playable with arrows + 3 action keys + number keys.
  4. Clear visual feedback.
  5. Progression after every match.
  6. No loss of permanent progress, ever.
  7. Abilities add strategy without confusion.
  8. Competitive but child-friendly.
  9. The player always understands what to do next.
  10. Minimal text in menus and interfaces.

5. Visual Direction

Correction / decision: the original recommended stylized 3D characters with a third-person 3D camera. Full 3D is not feasible in vanilla Canvas 2D, so the chosen direction is a 2.5D perspective ("Style A" interface): the simulation runs in flat field coordinates while the renderer projects the pitch into a tilted perspective that recedes toward a stadium horizon — the "most 3D" look achievable without a 3D engine. This is the implemented style (see js/match/render.js).

5.1 Visual Style

  • 2.5D perspective pitch rendered on Canvas: the field is projected with a 1/depth perspective so it tilts away from the camera; striped grass, white line markings, goals with nets, floodlights and a stadium horizon.
  • Shaded player figures: standing tokens (shadow, shaded torso, head, hair, shirt number) whose size scales with depth; the controlled player has a bright ring highlight and an active-ability aura.
  • Exaggerated ability effects: glow rings, trails, screen flashes — clear and rewarding for children.
  • Friendly, energetic tone; no attempt at realism.

5.2 Interface Style (matches the mockups in §30)

  • Dark blue backgrounds (#081226 family), bright blue interface elements (#3b82f6/#38bdf8)
  • Gold (#f5c542) for tournaments, trophies, and the selected menu item
  • Green (#34d399) for progress and successful actions; red only for negative events
  • Large circular ability icons; rounded buttons; high-contrast text
  • UI screens are DOM/CSS overlays; only the match itself is Canvas

5.3 Character Style

Players are drawn as stylized 2D tokens (head + shirt in menus; top-down token in matches). Customization changes skin tone, hair color, shirt style/colors, and number — all drawn procedurally (no art assets required for the MVP).

5.4 Camera

Correction: replaces the 3D "third-person elevated camera".

The implemented MVP uses a fixed full-pitch perspective camera: the whole 5-a-side pitch is visible at once, projected in 2.5D with the near (own) goal at the bottom of the screen and the far (opponent) goal near the horizon. The user always attacks "up" into the screen. A player-following scrolling camera is a post-MVP option.

7. Core Gameplay Loop

Open game
→ Select or create player
→ View tournament and next opponent
→ Play match (keyboard)
→ Win or lose
→ Receive experience and rewards
→ Advance (win) or replay the same match (lose)
→ Reach and win the final
→ Receive trophy
→ Unlock harder tournament
→ Continue indefinitely

8. Player Creation

8.1 Required Player Data

Name, appearance, country/team, shirt number, position.

8.2 Character Customization

MVP skin tone, hair color, shirt style, shirt number.
Post-MVP hair styles, face types, boots, gloves, wristbands, celebrations, accessories.

8.3 Playing Positions

Goalkeeper, Defender, Midfielder, Forward. The player's chosen position sets their starting role and attributes. Control normally stays with that footballer, but the user may hand control to a teammate — passing auto-switches to the receiver, and Space takes control of the outfield teammate nearest the ball when defending (§13.1). This keeps the user connected to the play instead of watching AI teammates handle the ball.

8.4 Position Primary Attributes

9. Player Statistics

Core statistics, each ranged 1–100:

speed, acceleration, shooting, passing, dribbling, tackling, strength, stamina, positioning, reflexes, goalkeeping

Statistics influence gameplay but must not make low-level players unusable (effects are scaled, never gating).

10. Match Structure

Correction: the original §10.3 timeline was internally inconsistent (it summed to 12:00 of "match time" while requiring 10 playable minutes, and the mockup HUD showed a clock of 07:32, impossible within a 5-minute half). The model below is the single source of truth.

10.1 Timing Model

  • Playable time: 10 minutes total — two halves of 5:00 playable each.
  • The match clock counts up from 0:00 to 5:00 within each half, with a half indicator (1T/2T in Spanish, 1H/2H in English). It can never display more than 5:00.
  • One hydration break per half, triggered at 2:30 of playable time in that half, lasting 1:00 of real time. The match clock and all gameplay are fully frozen.
  • Half-time break between halves (15 seconds by default, skippable with Enter).

Total playable time: exactly 10:00. Total real duration: ≈ 12:15. Breaks never consume playable time.

10.3 Match Clock Rules

The clock pauses during hydration breaks, half-time, goals/kick-off cinematics, and when the game is paused (P/Esc). It continues during normal stoppages (throw-ins, corners, goal kicks). All timing values live in the configuration file and are shortenable for testing.

11. Match Victory Rules

The winner is the team with the most goals at full time. Individual performance points never determine the winner.

11.1 Draws

Correction: the original recommended extra time (2×1 min) plus a penalty shootout for the first version. For the HTML MVP the document's own simplified alternative is adopted: an immediate penalty shootout after a draw. Extra time is deferred to post-MVP.
  • MVP On a draw, go directly to a penalty shootout: 5 kicks per team, then sudden death.
    • Shooting: ←/→/↑ choose corner, X shoots (a moving power gauge sets accuracy).
    • Saving: ←/→/↑ choose dive at the moment the AI shoots.
    • The user takes their team's kicks and defends in goal regardless of position (arcade rule, keeps every position engaged).
  • Post-MVP Two 1-minute extra-time periods (no hydration breaks) before penalties.

12. Defeat and Retry Rules

If the player loses: only the current match is repeated, against the same opponent in the same round. The tournament never restarts. Character level, statistics, experience, equipment, celebrations, and earned trophies are all preserved. The game may subtly ease difficulty after several consecutive defeats (see §24.1).

Same movement keys; the goalkeeper is confined near their area when the ball is far (AI-assisted positioning) and gains full control as the ball approaches. Dives use X plus a direction key; Z attempts a catch.

14. Core Football Mechanics

MVP running, sprinting (stamina), possession, passing, shooting with power charge, tackling, interception, goalkeeping, goal detection, out-of-bounds → throw-ins, corners, goal kicks (simplified: quick AI restart).

Post-MVP fouls and cards, offside, headers/aerial play beyond the bicycle kick.

Simplification confirmed from the original: the first version excludes offside and complex fouls. Performance-point entries that depend on cards/fouls (§19) stay defined in config but are inactive until fouls exist.

15. Ability Circle System

15.1 General Behavior

Ability circles appear on the pitch during play. Each has a unique icon and color, glows, is collected by moving over it, disappears on collection, and respawns later elsewhere.

15.2 Collection Flow

Circle appears → player moves over it → ability added to inventory
→ HUD slot fills (keys 1–5) → player presses slot key → effect occurs
→ ability removed from inventory

15.3 Inventory Limit

Maximum 5 stored abilities. While the inventory is full, new circles cannot be collected (walking over them does nothing except a brief "inventory full" flash). This is the simplest rule for children and is the confirmed MVP behavior.

15.4 Pitch Coordinate System and Spawn Rules

Correction: the original gave spawn distances in meters with no pitch scale. The pitch is now defined as a 105 × 68 unit logical coordinate system (1 unit = 1 m), rendered to canvas via a single scale factor. All distance rules use these units.
  • Spawn only in valid playable areas: never inside goals, never outside the pitch, never within 3 units of a player, never inside either penalty area (except goalkeeper-weighted abilities, which may spawn inside the user's own penalty area when the user is the goalkeeper).
  • Spawns must not repeatedly favor one team: alternate spawn halves with light randomization.
  • More powerful abilities are rarer (spawn weights, §17–18).

16.5 Bicycle Kick Activation Conditions

Pressing its slot key performs the bicycle kick only if all conditions hold:

  • Player is near the opponent's goal (configurable radius),
  • the ball is airborne above a minimum height (2D model: the ball has a simulated height value from lofted passes/clearances/crosses),
  • the player is correctly positioned relative to the ball,
  • no blocking animation is active.

If conditions are not met, the ability is NOT consumed and a short message is shown — ES: «Acércate a un balón aéreo para usar la chilenita.» · EN: “Move near an aerial ball to use the bicycle kick.”

To create the aerial ball on demand, the player has a lofted / chip kick (C, or L on WASD): it pops the ball almost straight up with a little forward drift so it falls back within reach, giving a window to activate the Chilenita. Without this there was no reliable way to raise the ball with the keyboard.

19.2 Match Rating

Scale 1.0–10.0, computed from position-appropriate contributions (goals, assists, passing, defense, goalkeeping, result). A goalkeeper is never penalized for not scoring — each position has its own rating weights in config.

20. Experience and Levels

Experience sources: match completion, victory, goals, assists, saves, tackles, tournament progression, winning the final. Level and experience are permanent — never lost on defeat.

20.4 Experience Formula (all values in config)

matchXP = 100                       // base, always granted
        + 100 × isVictory
        + performancePoints × 0.20
        + roundNumber × 25          // round 1 = quarter-final
        + 500 × isFinalVictory

Level curve: XP required for level n → n+1 = 100 × n (configurable). Level rewards: attribute points, and at milestone levels equipment/celebrations (§28).

21. Attribute Improvement

On level-up the player receives 2 attribute points (config: 1–3) to assign manually. Position-primary attributes cost 1 point per +1; all others cost 2 points per +1 (e.g., Shooting is cheap for forwards, Reflexes for goalkeepers, Tackling for defenders, Passing for midfielders).

22. Tournament Structure

22.1 MVP Tournament

Three rounds: Quarter-final → Semi-final → Final.

Correction: the original MVP scope said "two teams", which cannot supply three distinct opponents for three rounds. Corrected MVP content: the player's team plus an opponent pool of 4 AI teams; each round draws a different opponent from the pool (2 teams on the pitch per match). The full version keeps a wider pool and 5 rounds (Qualification, Round of 16, Quarter-final, Semi-final, Final).

22.2 Progression Rules

  1. Win → advance to the next round.
  2. Lose → replay the current match (same opponent).
  3. Win the final → trophy + unlock the next, harder tournament.

22.3 Infinite Tournaments

Correction: the original formula "1 + logarithm(tournamentNumber + 1) × 0.20" did not specify the logarithm base. It is the natural logarithm.
difficultyMultiplier = 1 + ln(tournamentNumber + 1) × 0.20
// T1 ≈ 1.14, T2 ≈ 1.22, T5 ≈ 1.36, T10 ≈ 1.48, T50 ≈ 1.79

The curve grows without bound but slowly, so later tournaments stay difficult yet possible. Each new tournament varies opponents, stadium theme (canvas palette), reward tier, and ability-spawn tuning.

24. Difficulty System

Difficulty scales AI quality, not raw physics: opponent decision speed, passing/shooting accuracy, goalkeeper reactions, defensive positioning, pressing intensity, ability usage, recovery speed. Opponents must never get unrealistic physical advantages.

24.1 Dynamic Assistance (hidden, configurable)

After repeated missed shots → slightly improved shot accuracy; after several defeats → easier opponent goalkeeper, more favorable ability spawns, reduced pressure, better teammate support. Subtle, capped, and resettable.

25. Artificial Intelligence

All 21 other footballers are AI-controlled. Requirements per role:

  • Team AI: attack/defense/transition states, ball recovery, support runs, passing, shooting, position-based behavior.
  • Goalkeeper AI: track ball, hold position by shooting angle, dive, catch, punch, rush out, distribute.
  • Defender AI: keep shape, mark, intercept, cover, tackle, clear danger.
  • Midfielder AI: offer passing options, control center, recover, connect defense–attack.
  • Forward AI: attacking runs, find space, shoot, press, position for rebounds.
  • User support: teammates continue play sensibly when the user is off the ball; a subtle indicator suggests positioning; C requests a pass. The user must never feel disconnected from the action.

Implementation: lightweight state machines + weighted target positions per role and game phase — no pathfinding library needed on an open pitch.

26. Single-Player Mode

Matches vs AI, infinite tournaments, player development, unlocks, trophies. Fully offline: the game is static HTML/JS/CSS with localStorage persistence — no server required.

27. Multiplayer Future

Unchanged in concept, deferred entirely out of the MVP: 1-vs-1 controlled-player mode with AI teammates, matchmaking by level, same match structure. Requires backend (§40), authentication, synchronization (WebSocket/WebRTC), reconnection, anti-cheat, safe usernames, parental protections. Online defeat never removes permanent progression. The offline game must be built so multiplayer can be added without refactoring match logic (deterministic, event-driven match engine).

28. Rewards

Confirmed reward types: equipment (shirts, kits, boots, gloves — cosmetic only, never pay-to-win) and special celebrations (knee slide, backflip, dance, bicycle-kick pose…). Sources: level-ups, tournament victories, trophy milestones; later: challenges, daily objectives, events.

MVP one unlockable kit variant + one unlockable celebration (shown as text/simple animation on the trophy screen).

29. Trophy System

Each completed tournament grants a trophy. Trophy room displays: total trophies, tournament number, completion date, difficulty, final opponent, final result.

Visual tiers cycle with upgrades (stars/frames) since tournaments are infinite:

31. Advertising Integration Future

Hydration breaks are the designated advertising space. Implementation: a placeholder DOM container (#ad-slot) inside the hydration-break overlay. Rules: ads never exceed the 1:00 break, never consume playable time, must be age-appropriate and compliant with child-privacy regulations (no personalized ads for child accounts). When no ad is available a localized gameplay tip is shown (MVP behavior). Optional rewarded ads (cosmetics, bonus XP) are future work and must never be required to retry a match.

Implemented with the Web Audio API; simple synthesized placeholder sounds are acceptable in the MVP.

34. Animation Requirements

Correction: the original listed 3D skeletal animations. In the 2D top-down style, animations are token states + procedural effects.
  • Player token states: idle, walk, run, sprint (motion trail), kick flash (pass/shoot), tackle slide, fall/recover, celebrate, dejected
  • Goalkeeper states: ready, dive left/right (token stretch), catch flash, punch flash, rush

38. Technical Architecture

Correction: replaces the Unity/Godot recommendation. Confirmed stack: vanilla JavaScript (ES modules) + Canvas 2D, no dependencies, no build step.

38.1 Stack

  • Rendering: one <canvas> for the match; DOM/CSS overlays for menus and HUD
  • Loop: requestAnimationFrame with a fixed logic timestep (60 Hz) and interpolated rendering
  • Persistence: localStorage (save data, settings)
  • Data: JSON files for localization, abilities, balancing, teams (fetched at boot; embedded as JS modules so file:// also works)
  • Audio: Web Audio API
  • Testing: plain JS unit tests (node:test) for pure logic modules; optional Playwright smoke test

44. Acceptance Criteria

  1. A user can create a player.
  2. The game starts in Spanish; the user can switch to English.
  3. The whole game is playable with keyboard only (no mouse required).
  4. The user controls exactly one footballer.
  5. A match contains two 5:00 playable halves; the HUD clock never exceeds 5:00 per half.
  6. Playable time totals exactly 10 minutes.
  7. One 1:00 hydration break occurs per half at 2:30; gameplay and clock stop completely.
  8. An advertisement placeholder (or tip) is visible during breaks.
  9. The team with more goals wins; performance points never decide the winner.
  10. A drawn match is resolved by the penalty shootout.
  11. Losing repeats only the current match; all progression is preserved.
  12. Five abilities can be stored; a sixth cannot be collected while full.
  13. Ability slots activate with keys 1–5.
  14. The Bicycle Kick activates only under valid conditions and is not consumed otherwise (message shown).
  15. Winning advances to the next round; winning the final grants a trophy, an equipment unlock, and a celebration.
  16. A new, harder tournament begins; the sequence is indefinite.
  17. Save data survives reloading and closing the browser.
  18. The game runs offline from static files in current Chrome and Firefox.

45. Instructions for the Coding AI

  1. Build modular ES modules exactly as in §38–39; match logic never touches the DOM.
  2. No hard-coded gameplay values — everything in data/config.js.
  3. Every visible string through i18n.js keys; Spanish is the fallback language.
  4. Keyboard input only through input.js abstract actions (enables future touch/gamepad).
  5. Implement save-data versioning from day one.
  6. Event-driven communication between engine, UI, and audio.
  7. Automated tests for: progression math, ability inventory rules, match timing (breaks freeze the clock), bicycle-kick conditions, localization completeness.
  8. Procedural placeholder graphics/sounds before final art.
  9. Configurable AI difficulty profiles.
  10. Hydration breaks must freeze both gameplay and clock; losing must never reset permanent progression; the Bicycle Kick must never be consumed on invalid activation.
  11. Keep monetization optional and completely separate from match progression.

46. First Technical Deliverable

A grey-box browser prototype: one canvas pitch, procedural player tokens, one controllable footballer (keyboard), basic AI players, one ball, pass/shoot/tackle, goals and score, full 10-minute match logic with hydration breaks, 5 ability slots with the 5 MVP abilities, victory screen, defeat + replay, basic 3-round tournament progression. Final graphics, multiplayer, advertising, and advanced customization are explicitly out of scope for this deliverable.

47. Final Product Summary

Camino a la Copa is a bilingual (Spanish-default) arcade football game for the browser, played entirely with the keyboard. The user creates and controls one footballer, chooses a position and team, and competes in an infinite sequence of elimination tournaments of increasing difficulty.

Matches contain exactly ten minutes of playable football in two 5-minute halves; each half has a one-minute hydration break during which everything stops (future ad space). Ability circles on the pitch grant collectible powers — up to five stored, activated with keys 1–5 — including Speed, Dribble, Tackle, Super Save, and the Chilenita bicycle kick.

Most goals wins; draws go to penalties. Losing only replays the current match and never costs progression. Winning a final grants a trophy, equipment, and celebrations, then unlocks a harder tournament — forever.

The game ships first as an offline vanilla-JS/Canvas experience against AI; multiplayer follows once the core is stable.
